## 🎯 命名规范概览

### 📋 核心命名格式
```
格式: 系统功能模块-子功能模块-年月日时分秒-环节代码-需求标题

基本结构:
[系统模块]-[子模块]-[时间戳]-[环节]-[功能描述]
```

### 📝 实际示例
```
需求编号: ECOM-PROD-20250731143000
目录名称: ECOM-PROD-20250731143000-产品管理功能/

文档命名:
├── ECOM-PROD-20250731143000-REQ-产品管理功能.yaml   (需求分析)
├── ECOM-PROD-20250731143000-ARCH-产品管理功能.yaml  (架构设计)
├── ECOM-PROD-20250731143000-DEV-产品管理功能.yaml   (开发任务)
└── ECOM-PROD-20250731143000-TEST-产品管理功能.yaml  (测试设计)
```

### 3. 时间戳格式 (14位数字)

#### ⏰ 时间戳规则
```yaml
格式: YYYYMMDDHHMMSS
说明: 年(4位) + 月(2位) + 日(2位) + 时(2位) + 分(2位) + 秒(2位)

示例:
  20250731143000: 2025年7月31日 14:30:00
  20250801090000: 2025年8月1日 09:00:00
  20251225180000: 2025年12月25日 18:00:00

用途:
  - 确保唯一性: 防止命名冲突
  - 时间追溯: 明确需求提出的具体时间
  - 版本管理: 便于按时间排序和管理
  - 影响分析: 了解需求的时间关联性
```

### 4. 环节代码 (2-4位英文代码)

#### 🔄 四大核心环节
```yaml
REQ: 需求分析 (Requirements Analysis)
  - 负责Agent: Agent-A (需求分析师)
  - 主要输出: EARS需求 + BDD场景
  - 协议标准: BDD/EARS结构化协议

ARCH: 架构设计 (Architecture Design)
  - 负责Agent: Agent-B (架构设计师)
  - 主要输出: 技术架构 + 设计决策
  - 协议标准: BDD/EARS结构化协议

DEV: 开发任务 (Development Tasks)
  - 负责Agent: Agent-C (开发工程师)
  - 主要输出: 任务分解 + 工作计划
  - 协议标准: TBDWBS结构化任务分解协议

TEST: 测试设计 (Testing Design)
  - 负责Agent: Agent-D (测试工程师)
  - 主要输出: 测试策略 + 测试用例
  - 协议标准: BTDTP结构化测试设计协议
```

### 5. 需求标题 (中文描述)

#### 📝 标题命名原则
```yaml
命名原则:
  - 简洁明了: 4-8个汉字，表达核心功能
  - 业务导向: 使用业务术语，避免技术术语
  - 统一风格: 同一系统内保持一致的命名风格
  - 易于理解: 业务人员可以直接理解含义

示例:
  ✅ 好的标题:
    - 产品管理功能
    - 用户注册流程  
    - 订单支付处理
    - 库存同步机制

  ❌ 避免的标题:
    - ProductCRUDModule (过于技术化)
    - 商品增删改查系统 (过于冗长)
    - SKU管理 (术语不够通用)
    - 业务模块A (缺乏描述性)
```

### 📋 文件组织原则
```yaml
原则1 - 需求独立性:
  - 每个需求形成独立的文件夹
  - 避免跨需求的文件依赖
  - 支持并行开发和维护

原则2 - 环节完整性:
  - 每个需求包含完整的四个环节文档
  - 环节间通过统一命名关联
  - 保持文档的一致性和追溯性

原则3 - 时间可追溯:
  - 通过时间戳实现版本控制
  - 支持需求的历史查询
  - 便于影响分析和变更管理

原则4 - 业务可理解:
  - 文件名直接体现业务含义
  - 便于业务人员查找和理解
  - 降低学习和使用成本
```

## 🎯 AI Agent应用指导

### 🤖 Agent使用规范

#### Agent-A (需求分析师)
```yaml
输入要求:
  - 明确系统功能模块和子功能模块
  - 提供准确的时间戳
  - 给出清晰的需求标题

输出规范:
  - 文件名: 系统模块-子模块-时间戳-REQ-需求标题.yaml
  - 文档ID: 系统模块-子模块-时间戳-REQ
  - 路径: 对应的需求目录下

示例:
  用户输入: "电商系统的产品管理功能，2025年7月31日14:30:00提出"
  Agent输出:
    - 文件名: ECOM-PROD-20250731143000-REQ-产品管理功能.yaml
    - 文档ID: ECOM-PROD-20250731143000-REQ
    - 目录: ECOM-PROD-20250731143000-产品管理功能/
```

#### Agent-B (架构设计师)
```yaml
输入来源:
  - 读取同目录下的REQ文档
  - 解析需求编号和标题
  - 继承命名规范

输出规范:
  - 文件名: [需求编号]-ARCH-[需求标题].yaml
  - 文档ID: [需求编号]-ARCH
  - 引用: 明确标注输入文档的完整路径

示例:
  输入文档: ECOM-PROD-20250731143000-REQ-产品管理功能.yaml
  输出文档: ECOM-PROD-20250731143000-ARCH-产品管理功能.yaml
```

#### Agent-C (开发工程师)
```yaml
输入来源:
  - REQ文档: 需求分析结果
  - ARCH文档: 架构设计决策
  - 同一需求编号的文档

输出规范:
  - 文件名: [需求编号]-DEV-[需求标题].yaml
  - 文档ID: [需求编号]-DEV
  - 任务分解: 基于TBDWBS协议

示例:
  输入文档: 
    - ECOM-PROD-20250731143000-REQ-产品管理功能.yaml
    - ECOM-PROD-20250731143000-ARCH-产品管理功能.yaml
  输出文档: ECOM-PROD-20250731143000-DEV-产品管理功能.yaml
```

#### Agent-D (测试工程师)
```yaml
输入来源:
  - 前三个环节的所有文档
  - 同一需求编号的完整文档链

输出规范:
  - 文件名: [需求编号]-TEST-[需求标题].yaml
  - 文档ID: [需求编号]-TEST
  - 测试设计: 基于BTDTP协议

示例:
  输入文档:
    - ECOM-PROD-20250731143000-REQ-产品管理功能.yaml
    - ECOM-PROD-20250731143000-ARCH-产品管理功能.yaml
    - ECOM-PROD-20250731143000-DEV-产品管理功能.yaml
  输出文档: ECOM-PROD-20250731143000-TEST-产品管理功能.yaml
```

## ✅ 质量检查清单

### 📋 命名规范检查
```yaml
基本格式检查:
  □ 系统模块代码: 2-4位英文大写字母
  □ 子模块代码: 2-4位英文大写字母  
  □ 时间戳格式: 14位数字 YYYYMMDDHHMMSS
  □ 环节代码: REQ/ARCH/DEV/TEST 其中之一
  □ 需求标题: 4-8个汉字，简洁明了

逻辑一致性检查:
  □ 同一需求的所有环节文档使用相同的需求编号
  □ 目录名与文档名前缀保持一致
  □ 时间戳符合实际提出时间
  □ 需求标题准确描述功能内容

文件组织检查:
  □ 每个需求独立目录
  □ 目录内包含四个环节文档
  □ 文档间的引用路径正确
  □ 共享组件单独管理
```

### 🔍 常见错误及修正
```yaml
错误1: 使用旧的REQ-前缀
  ❌ 错误: REQ-ECOM-PROD-20250731143000-REQ-产品管理功能.yaml
  ✅ 正确: ECOM-PROD-20250731143000-REQ-产品管理功能.yaml

错误2: 时间戳格式不规范
  ❌ 错误: ECOM-PROD-2025073114300-REQ-产品管理功能.yaml
  ✅ 正确: ECOM-PROD-20250731143000-REQ-产品管理功能.yaml

错误3: 环节代码不规范
  ❌ 错误: ECOM-PROD-20250731143000-REQUIREMENT-产品管理功能.yaml
  ✅ 正确: ECOM-PROD-20250731143000-REQ-产品管理功能.yaml

错误4: 需求标题过长或模糊
  ❌ 错误: ECOM-PROD-20250731143000-REQ-电商平台商品管理系统的CRUD功能模块.yaml
  ✅ 正确: ECOM-PROD-20250731143000-REQ-产品管理功能.yaml
```
